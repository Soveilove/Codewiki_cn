# Init business knowledge planning

Init plans pages around source-backed business capabilities, workflows and rules, not source directories. It retains every selected source entry, uses static dependency relationships only as batching clues, and lets the model assign a unique primary topic while other topics may read and reference shared source. Analysis batches are not page boundaries; failed ownership must trigger evidence-based recovery or fail explicitly, never produce numbered directory supplement pages. We chose bounded relationship-guided analysis plus model topic planning and cross-batch reconciliation over pure directory clustering, pure graph community detection or vector clustering because dependency graphs can be incomplete and names alone do not establish business meaning. Init is fixed and quality-checked first; old artifacts are user-cleared, and update alignment remains a separate later decision.

Language neutrality (2026-10-09): entry selection is per file, not per component-type whitelist. Every parsed source file keeps at least one analysis entry; the parser's own leaf entries are kept, and an unrepresented file is represented by its primary structure (class/interface/struct when present, else artifact, else the most-connected method/function). Any parser-emitted type can become an entry, so class-first (Java/C#) and function-first (Go/Rust/C/Python) repos get entries matching their own structure. Planning excerpts are syntax-neutral truncations, never keyword filters.

One completion definition (2026-10-09): page non-empty, child pages present, and every required source read — is enforced by shared, backend-agnostic validators (`generation_runtime.validate_document_complete` / `validate_source_reads`). The API (pydantic-ai) backend keeps its resumable retry loop; the subscription (caw) backend runs the same validators before saving, without adopting the retry loop or request semaphore.

Shared ownership (2026-10-09): a component claimed by several topics is normal, not a planning error. The first claiming topic keeps the full explanation; the others record it under `shared_components` and receive a `SHARED_COMPONENTS` instruction to explain only their own use and point at the primary page. Primary ownership stays unique, so no source is dropped and no page explains the same component twice.

Planning robustness (2026-10-09): one planning call assigns at most `max_planning_refs_per_call` references (default 80), because a few hundred references per response makes models stop mid-object, repeat references, or skip items. A truncated response is salvaged by decoding each complete `"topic": {...}` pair instead of discarding the whole call, so a syntax error only costs the unfinished tail.
